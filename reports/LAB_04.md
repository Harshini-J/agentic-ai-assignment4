## Part A · Mark the plan, place the checkpoints

The plan is the uncrashed run's (`planned-4201-s01-6407ec`): the model planned two searches, for a key term and an alternate one, so it has six steps.

Checkpoints are placed according to the type of each step rather than at fixed time intervals. Each write has a sync checkpoint immediately before execution: C1 before the PR creation (step 5) and C2 before the comment creation (step 6). Each checkpoint stores the exact arguments that will be sent to the write operation. Since the key is generated from these model-provided arguments, replay is safe only when the same arguments are used, and they must be saved to disk before the write executes. This design ensures that at most one write operation, the currently running one, is within the replay window. The four read operations do not require checkpoints because they are local, have no side effects, and can safely be repeated. As a result, a crash before C1 costs a restart: a new plan, the reads again and a new draft, about 14k tokens in the matrix against 17k for the uncrashed run, because nothing before the first write is saved. The resumed run may select a different file, which is acceptable. Overall, checkpoint placement limits the replay window to the currently executing step. However, whether a write killed during its own step actually happened must be determined using its key and, for the PR operation, its branch, rather than the checkpoint itself.

- Durability mode, and why: **sync**

I chose `sync`. The mode is set once for the entire run, and RepoMind has two write operations, one of which is an irreversible comment. Therefore, slide 12's rule of using sync for any run with an irreversible step applies. Exit would keep every checkpoint until the run ends, so a crash would lose all of them, since the run never reaches its end. Resuming the run would then allow the model to generate new arguments, potentially resulting in a new key and a duplicate write. Async writes checkpoints in the background, so a crash before the save completes could also lose the checkpoint containing the arguments for the pending write, leading to the same risk. Sync ensures that each checkpoint is saved to disk before the corresponding write begins, preserving the arguments needed for replay. Although this requires one SQLite write per checkpoint, the total cost is only two writes per run, which is small compared with the cost of the model calls.


- The weaker of the two writes, and why: **comment**

The comment is the weaker of the two writes. It has one defence against duplicates, its key, and the PR has two, its key and its branch. Both writes use a key derived from the run, the plan step and the arguments. However, this key can change when random keys are used (`KEY_MODE=uuid`) or when a replay causes the model to generate different arguments. If the comment's key changes, the check before execute finds nothing, because it searches the tracker only by that key, and a second comment is posted. The PR has an additional safeguard because its check before execute searches by branch rather than by key. Since the branch name (`repomind/issue-4201`) is fixed in the code and not generated by the model, the check still finds the existing open PR even if the key changes. In addition, a duplicate PR can be closed, whereas a duplicate comment remains visible to the issue's author. Therefore, I expect Part C to produce duplicate comments but not duplicate PRs.


## Part B · Kill it at every step

**The hand walk, written before the matrix.** The uncrashed run (`planned-4201-s01-6407ec`) planned six steps: read the issue, two searches, read a file, open the PR, post the comment.

**The crash I expect to be worst is `--die-during-step 6`** (`--die-after-step 6` replays the same way, from C2). The comment is committed to the tracker, but the process dies before receiving the reply, so the comment has been posted and RepoMind does not know whether it succeeded. This is the worst case because the comment is an irreversible write and its key is its only protection against duplication (Part A). Crashes at steps 1 to 4 require more of the run to be repeated, including the plan, but all those steps are reads.

- **Last checkpoint:** C2, saved in sync mode immediately before step 6. It contains the plan, steps 1 to 5 completed and step 6 running, the completed calls for steps 1 to 5 (including the PR's key), and the findings: label, file, and the comment's exact arguments.
- **Steps between the checkpoint and the crash, and the step running at the crash:** There are no steps between C2 and the crash because C2 is immediately before step 6. Step 6, the comment operation, is running when the crash occurs. The comment has already been committed, but its outcome is unknown to the process.
- **Side effects, and what closes each (a key, a recorded result, or nothing):** Steps 1 to 4 are reads with no side effects, closed by a recorded result: they are skipped and their saved results reused during resume. Step 5, the PR operation, has a side effect but is already completed, closed by a recorded result: it is in `completed_calls` with its key, so it is not replayed. Step 6, the comment operation, has an irreversible side effect, and only its key closes it. When the run resumes, it replays the comment using the exact arguments saved in C2, producing the same derived key. The registry's check before execute then finds the existing comment by that key and does not post another one. There is no branch-based or other safeguard for the comment.

**The cost of early crashes:** A crash at steps 1 to 4 leaves no checkpoint to resume from, so the run starts over with the same `run_id`. It generates a new plan, repeats the reads, and creates a new draft. This costs approximately another full run's worth of tokens, and the model may choose a different label or file. This is not considered a failure as long as the comment matches the findings in its own last checkpoint.

**Predictions:**
- **Crash at step 6 with derived keys:** One comment and one PR, with no model calls during resume.
- **Crash at step 6 with random keys (Part C):** Two comments and one PR, because the replay uses a new key that cannot match the existing comment. The PR is not replayed.
- **Entire matrix with derived keys:** Exactly one comment in all twelve cases, one PR exactly when the findings name a file and none when they say none, and each comment matches the label and file recorded in its own last checkpoint.
- **Entire matrix with random keys:** Duplicate comments occur only for crashes during or after step 6. At step 5, the PR is replayed with a new key, but the branch-based check finds the existing open PR and prevents a duplicate. The comment is then posted once. For crashes at steps 1 to 4, no write has occurred before the crash, so the restarted run posts the comment only once.
- **Plans may differ:** A crashed run's model may plan five steps (one search) instead of six; then step 5 is the comment in that run, and a kill at step 6 does not fire and is run again.

After running `make reset`, I set `KEY_MODE=uuid` for each crashed run and resumed using the plain `--resume` command. Both the original runs and their resumed runs used `key_mode: uuid`, as confirmed by their `run_start` and `resume` log entries. Ten of the twelve crashed runs planned five steps, meaning step 5 was the comment operation in those cases. A kill at step 6 only occurs when the plan contains six steps, so the step-6 cases were rerun until a run was successfully interrupted. Fifteen attempts completed without a crash and were excluded from the results: six attempts for the after-step-6 cases (`planned-4201-s01-73e907`, `-e76445`, `-9a6cea`, `-cc7823`, `-67e946`, and `-151f6d`) and nine attempts for the during-step-6 cases (`planned-4201-s01-75aca5`, `-611ab2`, `-f9b725`, `-6ca450`, `-4f9a5e`, `-0dc815`, `-3dcecf`, `-e319d5`, and `-4dae68`).

**Which N produced a second comment, counted from the tracker**

The values of N that produced a second comment, counted from the tracker by run_id (`Tracker().comments(run_id, 4201)` and `Tracker().prs(run_id, branch="repomind/issue-4201")`), were 5 and 6, and this occurred only when the kill landed on the comment step, after or during it. For five-step plans (N = 5), `planned-4201-s01-0d4348` (after) produced comments 9 and 10, while `planned-4201-s01-98a8a7` (during) produced comments 11 and 12. For six-step plans (N = 6), `planned-4201-s01-d117a1` (after) produced comments 20 and 21, while `planned-4201-s01-e9c32e` (during) produced comments 30 and 31. Each pair had identical comment bodies but different keys, as shown by `e56052a0…` and `7063baff…` for `0d4348`. Every crash at an earlier step (steps 1–4) resulted in exactly one comment that matched the run's findings.

No case produced a second PR: all twelve cases left exactly one open PR from `repomind/issue-4201`. When the PR operation was interrupted (N = 4, during or after on five-step plans), the replay used a new random key. However, Assignment 3's check before execute for `open_pr` searches by branch, and because the branch is fixed in the code, it found the existing open PR and prevented a duplicate. For `planned-4201-s01-2b04f6` (after), PR 7 was created with key `c17c0954…`, while the replay used `079b6f57…` and returned `already there: pr-7`. Similarly, for `planned-4201-s01-5f5262` (during), PR 8 was created with key `7de53166…`, while the replay used `dcc25c47…` and returned `already there: pr-8`. In contrast, the comment operation checks only by key. Since the replay generates a new random key, the check cannot find the existing comment, and a second comment is posted.

What the checkpoint did, and what the key did:
Both matrices crashed at the same steps and resumed from the same checkpoints, C1 before the PR and C2 before the comment. No resumed run repeated a call completed before its last checkpoint. The checkpoint determined where replay started and how much work ran again: crashes on a write required no model calls (0 tokens, compared with about 14k for crashes on a read) and reused the saved arguments. However, C2 is saved before the comment is sent, so it cannot confirm whether the comment was posted, and the comment is replayed. The key determined whether this created a duplicate. With derived keys, the comment-step crashes (`1b3aae`, `f39606`, `1fe0f0`) each left one comment because the replayed key matched. With random keys, all four comment-step crashes left two comments (9 and 10, 11 and 12, 20 and 21, 30 and 31) because the new key matched nothing. The PR never duplicated in either matrix because its check searches by branch, not by key. Therefore, the key, not the checkpoint, prevents duplicate writes, while the checkpoint preserves the arguments needed to reproduce the same key and avoids restarting the run.
